# M8 design: read view, release artifact, clean-clone run

Status: **proposal, for Trevor's review.** Coverage throughout: 10-K Item 1A and Item 7 for fiscal 2018–2025, and 10-Q
Part I Item 2 and Part II Item 1A filed January 2025 to September 2026, for 11 companies.

## 1. What the survey found (2026-10-20)

| | figure |
|---|---|
| Data a clean clone needs that git doesn't hold | the EDGAR cache (731 MB) and the model-response cache (141 MB), plus the timed-run latencies (`data/qa/latency.jsonl`, 10 KB). Everything else in `data/` regenerates from these. |

## 2. One-command reproduction (`python tools/reproduce.py`)

No API key needed (it unsets `ANTHROPIC_API_KEY`, and every recorder runs offline):

1. Check the release data is present and matches its manifest (sha256 per file).
2. Rebuild: `fetch --offline` → `parse` → `diff` → `facts` → `claims`.
3. Re-run every evaluation and report: the alignment evaluation; materiality (dev, test, Haiku, corpus, re-check);
   claims; the QA evaluation; spancheck.
4. Run the test suite.
5. **Fail if any committed file changed:** `git diff --exit-code -- docs tests corpus`. Passing means every published
   number was reproduced byte for byte.

## 3. The release artifact

- `tools/build_release.py` writes `filing-delta-data-<date>.tar.gz` (EDGAR cache, model cache, latencies) and a
  manifest of every file's sha256. The manifest is committed, so a clone knows exactly which data it expects.
- Hosted as a **GitHub Release on the private repo**: estimated 150–250 MB compressed, under GitHub's 2 GB per-asset
  limit. Downloaded with `gh release download` (or the Action's token), then verified against the manifest.
- Rejected: committing the data (too large, and CLAUDE.md keeps `data/` out of git), or Git LFS (quota, and it
  muddies the clean-clone promise).

## 4. Clean-clone GitHub Action (the M8 gate)

`.github/workflows/clean-clone.yml`, on push to `main` and on demand: a fresh `ubuntu-latest` runner, check out, set up
uv and Python 3.11, download and verify the release, run `tools/reproduce.py`. The README gets its status badge.

This is where platform differences surface (Linux vs. Windows, library versions, path handling). If the runner's
output differs, the diff says where, and that gets fixed rather than waived. Runtime is about 5–8 minutes per run on
the private repo's included Actions minutes.

## 5. Read view (`filing-delta serve`, local at 127.0.0.1)

A small FastAPI app over the derived JSON. It reads the same files the reports use; no database.

- **Changes:** pick a company, section and year pair. Each change shows its status (added, removed, reworded,
  moved), the inline word diff, and for Item 1A the material/cosmetic label with its code, rationale and verified
  evidence. Each change links to the exact source span and the filing on SEC.gov. There's a filter for material
  only.
- **Questions:** the 60 recorded questions with their answers and every citation highlighted in its filing text.
  Keyless, because they're recorded. With `ANTHROPIC_API_KEY` set, a box asks any question through the frozen
  pipeline (the "try-it path").
- **On every page:** what the tool does and doesn't claim. It reports what the filings say; Item 1A and Item 7 are
  management's unaudited narrative; nothing is advice or a forecast (pins 5 and 6, FD-DEC 016).
- **Tested two ways** (the M6 lesson): FastAPI test-client tests in the suite, and one Playwright pass in a real
  browser before the README screenshot.
- **DuckDB deferred** (named in the stack): JSON per filing is fast enough for 144 filings and keeps one source of
  truth. That gets a DECISIONS entry.
